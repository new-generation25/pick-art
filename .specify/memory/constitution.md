# pick-art (pica) Constitution

pick-art는 가까운 공연·전시·축제를 골라, 공식 출처로 확인해 날짜순으로 알려 주는 서비스다(브랜드 이름 `pica`).
이 문서는 기능을 명세·계획·구현할 때 지켜야 할 원칙이다. 근거가 된 결정은 `docs/`의 각 문서와 저장소 `CLAUDE.md`에 있다.

## Core Principles

### I. 확인한 정보만 공개한다 (NON-NEGOTIABLE)

- 공개 피드에 올리는 행사는 **날짜(시작·종료, YYYY-MM-DD)가 있고, 원본 링크가 지금 열리며(HTTP < 400), 이미 공개된 행사와 겹치지 않는 것**만이다. 검증은 `collector/tools/publish_verified.py`의 규칙을 따른다.
- 추측한 날짜·장소·요금을 쓰지 않는다. 확인 못 한 칸은 비우고, 이유를 기록한다.
- 포스터는 공식 출처의 원본만 쓴다(단체가 직접 준 리플렛·포스터 **파일** 포함). 현장 사진이나 대표 사진, 휴대폰으로 찍은 사진을 포스터처럼 쓰지 않고, 찾지 못하면 그렇게 표시한다.
- **예외 — 단체 제공(2026-11-26)**: 단체가 리플렛으로 직접 알려 준 행사(specs/013)는 공식 안내 주소가 없을 수 있다. 이때는 운영자가 이미지와 칸을 대조해 확인한 뒤에만 공개하고, 출처를 «단체 제공 · 단체 이름»으로 표시한다. 공식 안내 주소가 있으면 그 주소를 원본으로 쓴다. 날짜 규칙과 중복 확인은 그대로 적용한다.
- 끝난 수집분은 지우지 않고 `EXPIRED`로 남겨 중복 수집을 막는다.
- 근거: 사용자는 "링크가 작동하지 않거나 날짜가 정확하지 않은" 정보를 문제로 지적했다. 서비스의 존재 이유가 신뢰다.

### II. 작은 무대를 같은 무게로, 브랜드 가이드를 따른다

- 중소 예술단체·작은 공연장의 행사를 공공기관·문화재단 행사와 같은 형식·크기로 다룬다.
- 브랜드·화면·SNS·홍보 문구 작업은 `docs/BRAND_GUIDE.md`를 먼저 읽고 따른다. 가이드와 다르게 하려면 사용자에게 묻는다.
- **'경남'을 브랜드 자리(이름·슬로건·제목·헤더·프로필·표지)에 내세우지 않는다.** 지역은 행사 단위로 시군 이름만 쓴다.
- 날짜가 주인공이다. 목록·표지에서 가장 큰 정보는 "언제"다.
- 근거: 운영자가 서비스를 만든 이유, 2026-11-01 브랜드 결정.

### III. 보안과 비밀값

- 비밀값(키·토큰·비밀번호)은 출력·커밋·로그하지 않는다. `.env*`는 커밋하지 않는다.
- DB는 역할별 RLS를 유지한다: 익명은 공개 행사만 읽고, 관리자 데이터는 `profiles.role='admin'`만 쓴다. 회원은 자기 역할을 바꿀 수 없다. 새 테이블은 처음부터 정책을 갖고 만든다.
- 이 PC의 파이썬 실행·파일 읽기/쓰기를 하는 API는 배포 환경(`VERCEL=1`)에서 막는다(`frontend/src/lib/localOnly.ts`).
- 공개·외부로 나가는 동작(푸시·배포·SNS 게시·계정 설정 변경·메일 발송)은 사용자 승인 후에 한다.
- 근거: 2026-11-01 보안 정비(`supabase/migrations/20261101030000_security_rls.sql`).

### IV. AI 최소 개입으로 수집한다

- 수집은 공식 API(KOPIS 등) → 사이트 정의 파일(`collector/sources/*.json`, 선택자·규칙 날짜 파서) → 공식 블로그·인스타 순서로 하고, AI 추출은 대체 수단으로만 쓴다.
- 사이트별 코드를 파이썬에 넣지 않는다. 사이트가 바뀌면 정의 파일만 고친다. 정의가 0건을 내면 "정의 만료 의심"으로 보고한다.
- 정기 루틴(04:00·18:00)은 한 출처가 실패해도 멈추지 않고, 처리·실패·건너뜀을 숫자로 보고한다.
- 인스타그램 후보는 `REVIEW`로 쌓고 주간 검토로만 공개한다.
- **AI를 쓸 수 있는 곳(2026-11-26)** — AI는 옮기고·정리하고·돌리는 일을 돕고, 사실을 새로 만들거나 공개를 결정하지 않는다.
  - 수집: 공식 출처 글·이미지에서 날짜·장소·요금 등 칸을 옮겨 적기(근거 원문 함께), «정의 만료 의심» 출처의 정의 파일 수리 초안 만들기(사람이 확인한 뒤 반영), 새 출처 후보 찾기.
  - 제공 정보 가공: 단체가 올린 리플렛·포스터의 인쇄된 글자 읽기(specs/013), 같은 행사 판정 보조(중복 후보 제시), 분야·아이 대상 후보 제안, 띄어쓰기·표기 정리.
  - 자동화 가동: 예약작업으로 정기 일 돌리기(읽기·정리·리포트), 수집 실패 원인 요약과 재시도 판단, 운영 리포트·경고 요약.
- **AI가 하지 않는 것**: 인쇄·게시되지 않은 사실(연도·종료일·요금·시각·주소) 추측, 소개 글·«피카가 본 이유» 짓기, 포스터 고치기·새로 그리기, 로그인·차단 우회나 약관을 어기는 수집, 공식이 아닌 글을 근거로 칸 채우기, 사람 확인 없는 공개·삭제·대량 상태 변경, 돈·계정·설정 바꾸기.
- AI가 채운 값에는 누가 채웠는지(`extracted_by`·`read_by`)와 근거 원문(`raw`·`evidence`)을 남긴다. 공개는 검증 규칙(`publish_verified.py`)이나 운영자 확인을 거친다.
- 근거: 비용 0·재현 가능한 수집 방향(REVIVAL_PLAN), 2026-11-01 출처 확대, 2026-11-26 운영자 AI 범위 승인.

### V. 끝 조건을 먼저 정하고, 검증한 뒤 완료라고 말한다

- 작업마다 "무엇을 확인하면 끝인지"를 먼저 정한다. 버그는 재현 절차를 먼저 만들고 그것이 통과하면 끝이다.
- 완료 보고에는 실제로 실행한 확인(명령·숫자·화면)을 적고, 확인하지 못한 것은 못 했다고 쓴다.
- 프론트 변경은 최소 `npx tsc --noEmit`, 화면 변경은 브라우저 확인, 배포 변경은 배포 주소 확인까지 한다.
- 근거: 사용자의 전역 작업 지침.

## 추가 제약 (기술·운영)

- 스택: Next.js 16(App Router, Mantine, Tailwind 4) — 빌드는 **webpack**(`next build --webpack`), Supabase(서울), Vercel(함수 지역 `icn1`, 루트 `frontend`), 파이썬 수집기는 운영자 PC에서 실행.
- 메모리: 이 PC는 16GB다. 개발 서버는 webpack 모드·힙 2GB 상한으로 **한 번에 하나만** 띄운다. Turbopack 개발 서버는 쓰지 않는다(17GB 폭주 이력). 띄운 서버·브라우저 탭은 작업 후 닫는다.
- 데이터 삭제는 사용자 승인 후에만 한다. 관리자 화면의 영구 삭제는 확인 창을 거친다.
- 인스타그램 작업 전에는 `@picka.news` 로그인 상태를 확인한다. 게시·삭제·프로필 변경은 사용자 승인 후.

## 작업 방식

- 수정 단계마다 커밋한다. 커밋 메시지 끝에 공동 작성자 줄을 붙인다.
- 작업 브랜치에서 일하고, `main`에 합치는 것(= 자동 배포)은 사용자 승인 후에 한다.
- 결정·결과는 `docs/`에 남긴다(예: `docs/REPORT_*.md`, `docs/PLAN_*.md`). 사용자가 내린 결정은 원문과 날짜를 적는다.
- Spec Kit 절차: 새 기능은 `/speckit-specify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement` → `/speckit-converge`. 만들지 말지 정할 일은 아이디어 평가, 고장은 버그 수정 절차를 쓴다. 작은 수정에는 절차를 강제하지 않는다.

## Governance

- 이 문서는 명세·계획·구현에서 다른 관행보다 우선한다. 충돌하면 이 문서를 따르고, 바꿔야 하면 먼저 이 문서를 고친다.
- 개정은 사용자의 승인을 받아 `/speckit-constitution`으로 하고, 위 Sync Impact Report와 버전을 갱신한다. 원칙을 빼거나 뜻을 바꾸면 MAJOR, 원칙·절을 더하면 MINOR, 문구 정리는 PATCH.
- 계획(`/speckit-plan`)의 Constitution Check에서 위 다섯 원칙을 하나씩 확인한다. 어기는 설계는 이유와 대안을 계획서에 적는다.
- 실행 시점 안내: 저장소 `CLAUDE.md`, `docs/BRAND_GUIDE.md`.
