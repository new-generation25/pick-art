## User Scenarios & Testing *(mandatory)*

### User Story 1 - 한 화면에서 운영 상태를 본다 (Priority: P1) — 구현됨, 배포 전

운영자가 관리자 첫 화면(`/admin`)을 열면 지금 이상한 것, 행사 공급, 사람이 판단할 대기열, 가입 회원 수, 인스타 운영 지표가 한 화면에 보인다.

**Why this priority**: 지금은 «돌았는지·무엇이 비정상인지»를 로그 파일을 열어 봐야 안다. KOPIS 0건이 6일·11회 이어져도 아무도 몰랐다.

**Independent Test**: 관리자로 `/admin`을 열었을 때 활성 행사 수·검토 대기 수가 같은 시각 DB 직접 조회 값과 같고, 인스타 지표가 `metrics.json`과 같으면 통과.

**Acceptance Scenarios**:

1. **Given** 관리자 로그인, **When** `/admin`을 연다, **Then** «살펴볼 것» 목록과 공급·대기열·회원·인스타 칸이 보인다.
2. **Given** 일반 회원 또는 로그아웃, **When** `/admin` 또는 `ops_snapshots`를 읽는다, **Then** 화면은 홈으로 넘어가고 표 읽기는 빈 결과다.

---

### User Story 2 - 수집이 비정상이면 저절로 알 수 있다 (Priority: P1)

정기 수집이 돌 때마다 출처별 결과(발견·신규·중복·실패·정의 만료)가 숫자로 남고, 정해 둔 이상 규칙에 걸리면 대시보드에 빨간 줄이 생긴다. (텔레그램 알림은 2026-11-27 운영자 결정으로 없앴다(운영자 연락은 카카오톡으로 대체). 경고와 요약은 관리자 «현황»에서 본다.)

**Why this priority**: 전자동의 바탕이다. 판정이 없으면 자동 실행은 «돌았다»만 말하고 «됐다»는 말하지 못한다(REVIVAL 원인 ①).

**Independent Test**: KOPIS 요청을 일부러 실패시키는 시험 실행에서 «KOPIS 0건» 경고가 대시보드에 나오고, 되돌린 다음 실행에서 사라지면 통과.

**Acceptance Scenarios**:

1. **Given** 정기 실행 1회, **When** 끝난다, **Then** 처리한 출처 수만큼 출처별 결과 줄이 기록되고 대시보드 «출처별 최근 실행»에 보인다.
2. **Given** 같은 출처가 2회 연속 0건(또는 실패), **When** 두 번째 실행이 끝난다, **Then** 그 출처 이름이 든 경고가 생긴다.
3. **Given** 마지막 성공 실행이 14시간을 넘었다, **When** 대시보드를 연다, **Then** «정기 실행 누락» 경고가 보인다.
4. **Given** 이상 없음, **When** 하루가 지난다, **Then** 대시보드에 켜진 경고가 없다.

---

### User Story 3 - 사람이 판단할 것만 한 곳에 남는다 (Priority: P2)

인스타 수집분처럼 쌓여 있는 후보 중 사람이 볼 필요가 없는 것(이미 끝난 행사, 이미 공개된 행사와 같은 것)은 규칙으로 저절로 치우고, 남은 것은 «동의 필요»·«사람 판단»으로 나뉘어 관리자 인박스 한 곳에서 처리한다.

**Why this priority**: 2026-11-25 기준 인스타 REVIEW 663건 중 556건은 이미 끝난 행사다. 사람이 볼 것은 약 107건인데 663건이 «대기»로 보인다.

**Independent Test**: dry-run이 무더기별 건수를 내고, 적용 후 무더기 표시가 없는 REVIEW가 0건이며, 무작위 20건 확인에서 잘못 분류 0건이면 통과.

**Acceptance Scenarios**:

1. **Given** 끝난 날짜가 오늘 이전인 REVIEW, **When** 분류를 적용한다, **Then** `EXPIRED`가 된다(지우지 않는다).
2. **Given** 개인·단체·예술가 계정의 진행 중 행사, **When** 분류한다, **Then** «동의 필요»로 가고 공개되지 않는다.
3. **Given** 기관 계정 + 날짜·장소 추출 성공 + 원본 링크 열림, **When** 분류한다, **Then** «공개 후보»로 가고, 운영자가 인박스에서 묶음 승인해야 공개된다(헌장 IV: 인스타 후보는 검토로만 공개).

---

### User Story 4 - 지금 쓰는 코드만 남는다 (Priority: P3)

수집기 폴더와 저장소 루트에는 지금 실행 경로에 있는 코드만 남고, 일회성 스크립트는 `_attic/`으로 옮겨져 있다. 환경 파일은 하나다.

**Why this priority**: 위험보다 «어느 것이 지금 쓰는 것인지 모른다»가 문제다. 자동화가 늘수록 실행 경로가 분명해야 한다.

**Independent Test**: 이동 직후 정기 실행 1회의 출처별 발견 건수가 직전 회차와 같고, `npm run build`가 통과하면 통과.

**Acceptance Scenarios**:

1. **Given** 이동 목록 승인, **When** 옮긴다, **Then** `collector/` 최상위 .py가 15개 이하이고 삭제된 파일은 0개다.
2. **Given** 정리 후, **When** 관리자 메뉴의 모든 페이지를 연다, **Then** 모두 열린다.

### Edge Cases

- PC가 꺼져 정기 실행을 놓쳤다 → 켜진 뒤 1회 실행(스케줄러 StartWhenAvailable, 적용됨). 그사이 대시보드는 «누락»을 보여 준다.
- 구글드라이브(G:)가 없다 → 백업은 SKIP으로 끝나고 수집은 계속된다(적용됨).
- 출처 하나가 원래 행사가 적어 0건이 잦다 → 출처별로 0건 허용(기준 회수)을 둘 수 있어야 한다.
- 인스타 숫자가 오래됐다(인스타 회차가 실패) → 대시보드에 «n시간 전 것» 경고(적용됨, 30시간).
- 경고가 매번 같은 내용으로 반복된다 → 같은 경고는 한 줄로 두고 켜진 때와 풀린 때만 기록한다.
- 시험 실행이 실제 공개 피드를 바꾸면 안 된다 → 이상 판정 시험은 수집·공개 없이 결과 기록 단계만 흉내 낸다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 관리자 첫 화면은 «살펴볼 것», 행사 공급(활성·7/30/60일·시군·분야·0건 시군·포스터 없음), 최근 14일 출처 종류별 새 행사, 대기열 4종, 가입 회원 대비 1만 명, 인스타 지표를 보여야 한다. *(구현됨: 11a61a0)*
- **FR-002**: 인스타 지표는 이 PC의 `docs/insta/report`를 정기 실행 끝에 `ops_snapshots`로 올려 읽는다. 관리자만 읽는다. *(구현됨: cc46552, cf81dcc)*
- **FR-003**: 정기 실행은 출처별 결과를 숫자(발견·신규·중복·실패·정의 만료 여부·상태)로 남기고 최근 60회를 보존해야 한다.
- **FR-004**: 이상 판정 규칙은 한 곳(설정 파일)에 있고, 수집기가 판정해 결과(경고 목록)를 남긴다. 대시보드는 그 경고를 그대로 보여 준다. 규칙: 같은 출처 0건·실패 2회 연속, 마지막 성공 실행 14시간 초과, 정의 만료 의심, 자동 공개 0건 3회 연속.
- **FR-005**: (없앰, 2026-11-27) 경고와 요약은 관리자 «현황»에서만 본다. 따로 보내는 알림은 두지 않는다.
- **FR-006**: 공개 결과 파일은 `docs/`가 아닌 수집기 로그 폴더에 쓴다.
- **FR-007**: REVIEW 분류는 dry-run을 먼저 내고 운영자 승인 뒤 적용한다. 끝난 행사는 `EXPIRED`, 이미 공개된 것과 같은 것은 `DUPLICATE`, 남은 REVIEW에는 무더기 표시를 단다: 예술가·단체 계정(role artist·group)은 «동의 필요», 기관 계정(role official) + 날짜·장소 추출 성공은 «공개 후보», 나머지(제보 계정 informant는 공식 출처 찾기가 필요, 날짜 없음·포스터만인 글)는 «사람 판단». 새로 수집되는 REVIEW도 같은 규칙으로 정기 실행마다 표시한다.
- **FR-008**: 인박스는 «인박스(COLLECTED)·공개 후보·동의 필요·사람 판단·장소 확인» 탭으로 한 곳에서 처리하고, «공개 후보»는 묶음 승인할 수 있다. 공개는 `publish_verified` 검증(헌장 I)을 거친다.
- **FR-009**: 일회성 스크립트는 승인된 목록대로 `_attic/`으로 이동만 하고 지우지 않는다. `delete_*`는 `_attic/danger/`.
- **FR-010**: 수집기 환경 파일은 `collector/.env` 하나로 통일하고, 값은 출력하지 않는다.
- **FR-012**: 연결 실패·5xx·시간 초과로 실패한 출처는 같은 실행 끝에 1회 재시도한다. 정의 만료·발견 0은 재시도하지 않는다.
- **FR-013**: REVIEW 정리 적용은 바꾼 줄마다 `id·이전 상태·이전 무더기`를 목록 파일로 남기고, 그 파일로 되돌릴 수 있어야 한다.
- **FR-014**: 손으로 하는 단계는 «전자동 / 확인 한 번만 / 사람이 해야 함»으로 나눈 표([리포트 2-1절](../../docs/plan/restructure_2026-11-25.html))를 따르고, 사람 몫은 승인 대기함·장소 확인·수리 지시로만 남긴다.
- **FR-011**: 대시보드 배포(main 병합)와 각 단계의 설정 변경·파일 이동·스키마 변경은 운영자 승인 뒤에 한다.

### Key Entities

- **운영 스냅숏(ops_snapshots)**: 이름 하나에 JSON 하나. 인스타 지표(`insta_*`), 수집 실행 기록(`collector_runs`), 이상 판정(`collector_alerts`)을 담는다. 관리자만 읽고 수집기만 쓴다.
- **수집 실행 기록**: 실행 1회 × 출처 1곳 = 한 줄. 발견·신규·중복·실패·상태·정의 만료.
- **경고**: 규칙 이름, 대상(출처), 수준(이상·주의), 처음 생긴 시각, 풀린 시각.
- **검토 무더기**: REVIEW 후보의 분류 결과(만료·중복·동의 필요·공개 후보·사람 판단).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 수집 이상(출처 0건 연속·실행 누락)을 다음 정기 실행 안(최대 약 17시간)에 대시보드로 알 수 있다. 기준선: KOPIS 0건을 6일 동안 몰랐다.
- **SC-002**: 사람 판단 대기열의 «보이는 건수»가 실제로 볼 것과 같다. REVIEW 663(11/25) → 적용 후 끝난 것 약 556건은 EXPIRED, 남은 약 107건은 모두 무더기 표시(동의 필요·공개 후보·사람 판단)를 갖는다.
- **SC-003**: (없앰, 2026-11-27) 따로 보내는 수집 보고를 두지 않는다.
- **SC-004**: 아침 정기 실행 누락률: 11/10~25 기준 16회 중 8회 → 적용 후 2주 동안 0회(PC가 켜진 날 기준).
- **SC-005**: `collector/` 최상위 .py 51개 → 15개 이하, 저장소 루트 일회성 스크립트 34개 → 0개, 삭제 0개.

## Assumptions

- 정기 수집은 계속 이 PC(작업 스케줄러 08:20·15:00)에서 돈다. 클라우드 이전(R6)은 이 기능 밖이다.
- 인스타 게시·참여 예약 작업(10시·16시 Claude 세션)은 그대로 두고, 그 결과만 대시보드로 가져온다.
- 소규모 행사 공개에는 단체의 동의가 필요하다는 운영 원칙(docs/insta/process.html)은 바뀌지 않는다.
- 새 테이블은 이미 적용한 `ops_snapshots` 하나로 충분하다. R1·R2는 스키마 변경 없이 한다. 무더기는 `raw_posts.content.review_bucket`에 적고 상태는 기존 값(REVIEW·EXPIRED·DUPLICATE)만 쓴다 — 다른 세션이 쓰는 `review_instagram.py`가 그대로 동작하게.
