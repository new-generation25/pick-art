## 1. 수집 실행 기록을 어디에 남기나

- **Decision**: `ops_snapshots`에 `collector_runs`(최근 60회 × 출처별 줄)와 `collector_alerts`(지금 켜진 경고 + 최근 풀린 경고) 두 이름으로 남긴다.
- **Rationale**: 이미 적용한 표라 스키마 변경이 없다. 관리자만 읽는 RLS가 이미 있다. 60회 × 31출처 ≈ 1,900줄, 한 줄 200바이트면 약 0.4MB로 jsonb 한 칸에 충분하다.
- **Alternatives**:
  - `crawl_logs`에 출처별 줄을 쓴다: 컬럼이 글자(result_summary)뿐이라 숫자 칸을 더하는 마이그레이션이 필요하고, 수동 요청 기록과 섞인다.
  - 새 표 `collector_runs`: 쿼리는 편하지만 테이블이 하나 더 늘고 보존 정리(삭제)가 필요하다.

## 2. 이상 판정은 누가 하나

- **Decision**: 수집 이상(출처 0건 연속·실패·정의 만료·자동 공개 0건 연속)은 **수집기**가 실행 끝에 판정해 `collector_alerts`에 쓴다. «정기 실행 누락»(마지막 실행이 14시간 넘음)은 실행이 없으면 판정할 주체가 없으므로 **대시보드**가 `collector_runs`의 마지막 시각으로 판정한다. 공급·대기열 경고는 지금처럼 대시보드가 DB로 판정한다.
- **Rationale**: 규칙을 한 언어·한 파일에 둔다(`collector/rules/alerts.json`). 대시보드와 수집기가 같은 규칙을 두 번 구현하지 않는다. 누락만은 정의상 실행 밖에서 봐야 한다.
- **Alternatives**: 대시보드가 실행 기록을 읽어 모두 판정 → 실행이 끝난 자리에서 판정을 남길 주체가 없다.

## 3. 따로 보내는 알림

- **Decision**: 두지 않는다(2026-11-27 운영자 결정). 전체 보고는 로그 파일에, 경고와 회차 요약은 관리자 «현황»에 남는다.
- **Rationale**: 매일 같은 «⚠️ 실패 2»가 반복돼 KOPIS 0건이 묻혔다. 경고를 상태(켜짐·풀림)로 두면 같은 경고가 되풀이되지 않는다.

## 4. 출처별 0건 기준

- **Decision**: 기본 «2회 연속 0건이면 주의, 실패(FAIL)는 1회로 이상». 출처 정의 파일(`sources/<slug>.json`)의 `expect`에 `quiet_runs_ok`(0건 허용 회수)를 둘 수 있게 한다. KOPIS는 코드 기본값으로 2.
- **Rationale**: 11/25 15:00 실행에서 웹사이트 28곳 중 신규가 있었던 곳은 4곳뿐이다(남해·부산문화회관·부산문화재단·비짓부산). «신규 0»이 아니라 **«발견 0»**을 기준으로 해야 정상 출처를 경고하지 않는다. 발견 0은 목록 자체를 못 읽었다는 뜻이다.
- **Alternatives**: 신규 0 기준 → 거의 모든 출처가 매번 경고된다.

## 5. REVIEW 정리 규칙

- **Decision**: 새 도구 `tools/triage_review.py --dry-run | --apply`.
  1. 끝나는 날(없으면 시작일) < 오늘 → `EXPIRED`
  2. 공개된 행사와 같음(review_instagram의 기존 중복 판정 재사용) → `DUPLICATE`
  3. 남은 REVIEW에 `content.review_bucket`: role artist·group → `consent`, role official + 날짜·장소 있음 → `candidate`, 나머지 → `human`
  - 정기 실행에서 인스타 수집 뒤 `--apply`를 자동으로 돌린다(1·2번은 사람 판단이 필요 없는 정리, 3번은 표시만).
- **Rationale**: 상태 값을 새로 만들지 않아 `review_instagram.py`(다른 세션이 씀)가 그대로 동작한다. EXPIRED는 헌장 I의 «지우지 않고 EXPIRED로»와 같다.
- **Alternatives**: 새 상태 값(NEEDS_CONSENT 등) → 다른 세션 도구·문서를 함께 고쳐야 한다.
- **첫 적용 전 dry-run 숫자를 운영자에게 보이고 승인받는다**(데이터 상태를 대량으로 바꾸는 일).

## 6. 인박스 통합 범위

- **Decision**: `/admin/inbox`에 탭을 더한다: 인박스(COLLECTED) · 공개 후보 · 동의 필요 · 사람 판단. 장소 확인은 기존 `/admin/venues` 링크로 둔다(화면이 이미 있음). «공개 후보» 탭의 묶음 승인은 선택한 raw_post id들로 `publish_verified --ids`와 같은 검증을 거친다.
- **Rationale**: 배포 환경에서는 파이썬을 못 돌리므로(헌장 III, localOnly), 묶음 승인은 브라우저에서 검증 규칙(날짜·중복)을 적용하고 링크 검사는 서버 라우트에서 한다 — 또는 승인 표시만 하고 다음 정기 실행이 `publish_verified --ids`로 공개한다. **후자를 택한다**: 검증 규칙이 파이썬 한 곳에만 있게 한다. 화면에는 «다음 정기 실행에서 공개됨»으로 표시한다.
- **Alternatives**: 프론트에 검증 규칙을 다시 구현 → 규칙이 두 군데가 된다.
