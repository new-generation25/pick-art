# Feature Specification: 리플렛 한 장으로 행사 등록 (단체 제공)

**Feature Branch**: `revive/2026-10` (명세 `specs/013-leaflet-intake`) | **Created**: 2026-11-26 | **Status**: 구현·로컬 검증 완료(1차) — 운영자 11/26 결정 반영(아래 «운영자 결정»). 배포는 승인 뒤

**Input**: 운영자 요청(11/26, 원문) "단체 입장에서 리플렛 한장 이미지를 보내거나 사진을 찍어서 보내면 자동으로 우리 포맷으로 전환되어 db에 등록되도록 하는 시스템 구축". 007(행사 제보, `specs/007-report-tip`)을 넓힌다. 제휴 단체 약관 초안 제6조 3항이 이 기능을 «준비 중»으로 이미 적어 두었다: "단체 또는 운영자가 내용을 확인한 뒤에 게재합니다."

**한 줄 정의**: 단체가 리플렛·포스터 이미지(파일 또는 휴대폰 사진)를 올리면, AI가 글자를 읽어 피카 입력 칸(제목·날짜·시간·장소·관람료·예매 방법)에 채운 **초안**을 만들고, 단체가 칸을 확인·고친 뒤 보내면 `raw_posts`에 `REVIEW`로 쌓인다. 공개는 운영자 검토 뒤에만 한다. 자동 공개는 없다.

근거 조사(현재 AI 사용 상태, 키 이름, 비용 단가, 저장 위치 비교)는 [research.md](research.md)에 있다.

## 실사이트 시험과 고친 것 (2026-11-26)

- 운영자 «단체가 업로드 했다고 가정하고(데이터 넣어서) 구동되는지 테스트해»: picka.news에 시험 리플렛 2장(포스터 파일: 연도·개인 휴대전화·예매 주소·여러 회차 / 휴대폰 사진: 연도 없음) 업로드 → 클로드 예약작업 실제 실행(첫 실행은 운영자가 권한 승인) → «대기 2건 읽어 저장» → 파일은 날짜 2026-12-18~20·휴대전화 미기재, 사진은 날짜 빈칸·지역 짐작 없음 → 관리자 화면 등록 → 상세 «단체 제공» 표시 확인 → 시험 데이터 모두 삭제.
- 찾은 문제 1: 포스터 없는 행사 상세에 깨진 그림(대체 파일 `/images/placeholder.webp`가 저장소에 없음 — 리플렛과 상관없이 포스터 없는 모든 행사). → `PosterViewer`가 «포스터 없음» 칸을 그림. 등록 시 포스터 없으면 `null`.
- 찾은 문제 2: 포스터로 쓴 리플렛 이미지에 개인 휴대전화가 그대로 보임. → 예약작업 결과에 `personal_info_visible`(이미지에 개인 휴대전화·계좌·개인 메일이 보이면 true, 칸에서 걸러진 게 있으면 자동 true)을 더하고, 관리자 화면에서 그 이미지는 포스터로 쓸 수 없게 막음.
- 운영자 «개인 휴대전화는 우리 사이트에서는 노출되지 않게 하고, 해당 출처로 이동해서 확인하도록해»: 사이트 전체 규칙으로 `lib/privacy.ts maskPersonalPhones` — 상세 화면·공유 설명·캘린더(.ics)에서 휴대전화를 «(개인 연락처는 원본 안내에서 확인)»으로 바꾼다(DB 원문은 그대로, 유선·대표번호는 그대로). 11/26 공개 행사 중 설명에 휴대전화가 든 것 17건.

## AI 사용 범위 (헌장 2.0.0 IV에 반영, 2026-11-26)

원칙은 그대로: **AI는 옮기고·정리하고·돌리는 일을 돕고, 사실을 새로 만들거나 공개를 결정하지 않는다.** 모든 AI 결과는 출처(`extracted_by`·`read_by`)와 근거 원문(`raw`/`evidence`)을 남긴다.

| 영역 | 해도 되는 것 | 하면 안 되는 것 |
|---|---|---|
| 수집(크롤링) | 공식 출처 글·이미지에서 날짜·장소·요금 등 칸 옮겨 적기(근거 원문 함께), 사이트 구조가 바뀌어 «정의 만료 의심»이 뜬 출처의 정의 파일 수리 초안 만들기(사람 확인 뒤 반영), 새 출처 후보 찾기 | 로그인·차단 우회, 출처 약관을 어기는 수집, 공식이 아닌 글을 근거로 칸 채우기 |
| 제공 정보 가공 | 리플렛 글자 읽기(이 명세), 같은 행사 판정 보조(중복 후보 제시), 분야·아이 대상 후보 제안, 띄어쓰기·표기 정리 | 없는 연도·요금·시각 추측, 소개 글·«피카가 본 이유» 짓기, 포스터 고치기·새로 그리기 |
| 자동화 가동 | 예약작업으로 정기 일 돌리기(읽기·정리·리포트), 수집 실패 원인 요약과 재시도 판단, 운영 리포트·경고 요약 | 공개·삭제·대량 상태 변경을 사람 승인 없이 하기, 돈·계정·설정 바꾸기 |

헌장 문구 제안(IV 끝에 덧붙임): «AI는 공식 출처나 단체가 준 자료의 글자를 칸으로 옮기고, 정리·분류 후보를 내고, 예약작업으로 정기 일을 돌리는 데 쓸 수 있다. 이때 근거 원문을 함께 남기고, 인쇄·게시되지 않은 사실을 만들지 않으며, 공개·삭제는 검증 규칙이나 사람의 확인을 거친다.» — 바꾸려면 `/speckit-constitution`(MINOR).

| V. 끝 조건 먼저 | 아래 «끝 조건»의 시험을 통과해야 완료다 |

### 헌장 IV 예외의 범위 (AI가 해도 되는 것 / 안 되는 것)

**해도 되는 것**
- 올라온 이미지 한 장에 **인쇄된 글자를 읽어** 정해진 칸에 옮긴다. 칸마다 «읽은 원문 그대로»(예: `12.5(금) 19:30`)와 확신 정도(높음·낮음·못 읽음)를 함께 낸다.
- 칸을 고를 때의 분류(이 글자가 장소인지 주최인지)까지만 한다.

**하면 안 되는 것**
- 공개(발행)하지 않는다. AI 결과는 `REVIEW` 초안까지만 간다.
- **추측하지 않는다**: 인쇄되지 않은 연도·종료일·요금·장소 주소를 채우지 않는다. «무료일 것 같다», «매일 같은 시간일 것 같다»를 쓰지 않는다.
- **지어내지 않는다**: 소개 글을 새로 쓰거나 늘리지 않는다. 출연진·장르를 이미지에 없는 내용으로 채우지 않는다.
- 날짜를 직접 YYYY-MM-DD로 정하지 않는다. AI는 원문 글자만 내고, 날짜 변환은 수집기와 같은 규칙 날짜 파서가 한다(파서가 못 바꾸면 빈칸).
- 이미지를 고치거나 새로 그리지 않는다(BRAND_GUIDE 0-7, 5-5).
- 개인 휴대전화 번호·개인 이메일을 공개용 칸에 넣지 않는다(아래 «개인정보»).

이 예외는 이 기능의 «리플렛 읽기»에만 적용한다. 수집기의 다른 경로에서 AI를 켜는 근거로 쓰지 않는다. 헌장 문구에 예외를 적을지(개정 MINOR)는 운영자가 정한다(«정할 것» 6).

## User Scenarios & Testing

### User Story 1 — 단체가 리플렛을 올린다 (P1)

단체 담당자가 `/tip`(또는 새 `/tip/leaflet`)에서 «리플렛·포스터로 등록하기»를 누르고, 휴대폰으로 리플렛을 찍거나 이미지 파일을 고른다. 올리기 전에 권리 확인 체크(«정할 것» 4)를 해야 버튼이 켜진다. 올리면 «글자를 읽는 중…»이 보이고 수 초 안에 확인 화면(US2)으로 넘어간다.

**Why this priority**: 운영자 요청의 시작점. 이것만 있어도(읽기 실패 시 빈 양식으로) 007 제보보다 단체 손이 덜 간다.

**Independent Test**: 시험 회원으로 JPEG 한 장을 올려 비공개 버킷에 `<user_id>/<제출 id>.jpg`로 저장되고, 익명·다른 회원은 그 파일을 읽지 못하는지 확인.

**Acceptance Scenarios**:
1. **Given** 로그인 회원, **When** 3MB JPEG을 권리 체크 후 올리면, **Then** 비공개 버킷에 저장되고 제출 기록이 `uploaded`로 생긴다.
2. **Given** 권리 체크를 안 함, **When** 올리기를 누르면, **Then** 버튼이 꺼져 있어 보낼 수 없다.
3. **Given** PDF·GIF·20MB 파일, **When** 고르면, **Then** «JPG·PNG·WEBP·HEIC, 10MB 이하만 받아요»가 표시되고 저장되지 않는다.
4. **Given** 오늘 이미 5장을 올린 회원, **When** 6번째를 올리면, **Then** 거절되고 내일 다시 하라고 표시된다.
5. **Given** 이달 AI 비용 상한에 닿음, **When** 올리면, **Then** 이미지는 저장되고 AI 읽기 없이 빈 확인 화면이 나온다(«지금은 자동 읽기를 쉬고 있어요. 직접 적어 주세요»).

### User Story 2 — 단체가 읽은 칸을 확인하고 보낸다 (P1)

확인 화면 왼쪽(휴대폰은 위)에 올린 이미지, 오른쪽에 칸이 나온다: 행사 이름, 시작일, 종료일, 회차 시간, 장소, 지역, 관람료, 예매 방법(전화·링크·현장), 공식 안내 주소(선택 또는 필수 — 원본 링크 문제 (a)/(b)에 따름), 주최·단체 이름, 문의 연락처. 칸마다 «리플렛에서 읽은 글자»가 작게 붙고, 못 읽은 칸은 비어 있고 «못 읽었어요 — 직접 적어 주세요»가 붙는다. 확신이 낮은 칸은 테두리로 표시된다. 단체는 고치고, «내용이 리플렛과 같습니다» 체크 후 보낸다.

**Why this priority**: 헌장 I을 지키는 핵심 장치. AI 결과를 사람이 먼저 확인한다(약관 제6조 3항 «단체 또는 운영자가 확인»).

**Independent Test**: 연도 없는 리플렛(`12.5(금)~12.7(일)`)을 올려 날짜 칸이 비어 있고, 단체가 2026을 골라 넣은 뒤 보내면 `raw_posts`에 `REVIEW`로 한 줄이 생기는지.

**Acceptance Scenarios**:
1. **Given** 연도가 인쇄되지 않은 리플렛, **When** 확인 화면이 열리면, **Then** 시작일·종료일 칸은 비어 있고 «리플렛에서 읽은 글자: 12.5(금)~12.7(일)»과 «2026년 12월 5일은 금요일입니다» 같은 요일 대조 안내만 나온다(값은 채우지 않음).
2. **Given** 날짜 칸이 비어 있음, **When** 보내기를 누르면, **Then** «시작 날짜를 넣어 주세요»로 막힌다(007 `checkTip`과 같은 검사).
3. **Given** 단체가 칸을 고침, **When** 보내면, **Then** AI가 읽은 값과 단체가 확정한 값이 **둘 다** 남는다(운영자가 무엇을 고쳤는지 볼 수 있게).
4. **Given** 문의 칸에 `010-` 번호가 읽힘, **When** 확인 화면이 열리면, **Then** 그 칸은 «공개하지 않음»이 기본으로 켜져 있고 «단체 대표 번호라 공개해도 됩니다»를 골라야만 공개 후보가 된다.
5. **Given** 리플렛이 행사 2개 이상(시리즈·축제 프로그램표), **When** 읽으면, **Then** 첫 화면에 «행사가 여러 개로 보입니다. 하나씩 올려 주시거나 운영자에게 맡겨 주세요»를 표시하고 억지로 한 칸에 합치지 않는다.

### User Story 3 — 운영자가 검토하고 공개한다 (P1)

운영자는 관리자 화면(지금 `REVIEW`는 «앱 화면 없음» — `frontend/src/app/admin/page.tsx` 타일)에서 «단체 제공» 무더기를 열어, 이미지·AI 값·단체 확정 값·고친 칸 표시·권리 체크 기록·제출 회원을 한 화면에서 본다. «공개», «고쳐서 공개», «단체에 묻기(메모)», «반영 안 함»을 고른다. 공개는 기존 발행 규칙(날짜·중복)을 거친다.

**Why this priority**: 공개 전 마지막 확인. 이것 없이는 US1·2의 결과가 영영 공개되지 않는다.

**Independent Test**: US2로 쌓인 한 줄을 «공개»하면 `events`에 1줄, `raw_posts.status=PUBLISHED`, 원본 링크·출처 표기가 선택한 방식((a)/(b))대로 들어가는지.

**Acceptance Scenarios**:
1. **Given** `REVIEW`(단체 제공) 한 줄, **When** 운영자가 공개하면, **Then** `events.source='단체 제공'`(또는 결정된 이름), `original_url`이 (a) 단체 SNS 주소 / (b) 피카 제공 이미지 페이지, `poster_image_url`은 권리 체크가 있고 «원본 파일»일 때만 채워진다.
2. **Given** 이미 공개된 행사와 제목·시작일·지역이 같음, **When** 공개하려 하면, **Then** `publish_verified.py`와 같은 중복 판정으로 막히고 «이미 공개됨»으로 표시된다(정보 보강은 기존 행사 고치기로).
3. **Given** 운영자가 «반영 안 함», **Then** `raw_posts.status='REJECTED'`, 이미지는 보유 기간(«정할 것» 7) 뒤 지운다. 지우기 전에는 지우지 않는다.
4. **Given** 운영 대시보드, **Then** «사람 판단 대기»에 «단체 제공» 건수가 보인다(007 «신고·제보»와 같은 자리).

### User Story 4 — 단체가 보낸 것의 상태를 본다 (P3)

단체 회원은 «내가 보낸 리플렛»에서 상태(검토 대기 / 공개됨[행사 링크] / 반영 안 함[사유]) 를 본다. 공개 뒤 정정은 007 «정보가 틀렸어요»로 한다.

---

### Edge Cases

- **사진 품질**: 기울어짐·빛 반사·일부 잘림 → 못 읽은 칸은 비움. 전부 못 읽으면 빈 양식(= 007 제보 양식)으로 이어진다.
- **휴대폰 사진을 포스터로 쓰는 문제**: 헌장 I «현장 사진이나 대표 사진을 포스터처럼 쓰지 않는다». 인쇄물을 찍은 사진은 **읽기용**으로만 쓰고, 공개 포스터는 단체가 «원본 파일입니다»를 고른 이미지(또는 따로 올린 원본)만 쓴다. 사진뿐이면 포스터 칸을 비우고 «포스터 없음»으로 둔다.
- **같은 리플렛을 여러 번 올림**: 같은 회원·같은 이미지 해시는 새로 읽지 않고 이전 제출로 보낸다(비용 절약).
- **행사 여러 개 / 회차표**: US2-5. 회차 시간은 «회차 시간» 칸에 원문대로(`12.5 19:30 / 12.6 15:00·19:00`) 둔다.
- **지난 행사**: 종료일이 오늘보다 앞이면 «이미 끝난 행사입니다»로 보내기를 막는다(발행 규칙의 «기간 지남»과 같음).
- **이미지 속 다른 글자**: 후원 기관 로고·QR 코드. QR은 읽지 않는다(링크를 따라가 내용을 가져오지 않음). 예매 링크는 인쇄된 주소 글자만 옮긴다.
- **악용**: 행사와 무관한 이미지·광고 → 운영자 «반영 안 함». 하루 한도와 로그인 요구로 양을 막는다.
- **AI 응답 실패·시간 초과**: 한 번 다시 하고, 그래도 실패하면 빈 양식으로 이어간다. 실패도 비용 집계에 넣는다(요청이 나갔다면).

## Requirements

### Functional Requirements

**이미지 받기·저장**
- **FR-001** 새 Supabase Storage 버킷(가칭 `leaflets`)은 **비공개**(`public=false`)로 만들고, 파일 크기 상한 10MB, 허용 형식 `image/jpeg, image/png, image/webp, image/heic, image/heif`를 버킷 설정(`file_size_limit`, `allowed_mime_types`)으로 건다. 기존 `posters`·`event-images`는 공개 버킷이라 쓰지 않는다.
- **FR-002** 경로는 `<auth.uid()>/<제출 id>.<확장자>`. RLS: 회원은 **자기 폴더에만** 넣고 읽는다, 관리자는 모두 읽는다, 익명은 아무것도 못 한다, 수정·삭제는 관리자(또는 서비스 키)만.
- **FR-003** 올리기 전에 브라우저에서 긴 변 2048px 안팎으로 줄여 다시 저장한다(용량·AI 토큰 절약). 다시 저장하면서 **사진 위치(EXIF GPS) 등 메타데이터를 지운다**. HEIC를 브라우저가 못 여는 경우(데스크톱 Chrome 등)는 원본 그대로 올리고 서버에서 처리한다 — 계획 단계에서 실제 기기로 확인.
- **FR-004** 하루 한도: 회원당 5장(007의 하루 10건과 별도). 같은 이미지(해시 같음)는 다시 읽지 않는다.

**AI 읽기**
- **FR-010** AI는 이미지 한 장과 고정 지시문을 받아 **정해진 JSON 칸만** 돌려준다(구조화 출력). 칸마다 `{raw: 읽은 원문, value: 칸 값 또는 null, confidence: high|low|none}`. 칸: title, date_text, time_text, venue, region_hint, price_text, booking_text, booking_url, organizer, contact, multiple_events(참/거짓).
- **FR-011** 날짜는 AI 값이 아니라 `date_text` 원문을 **규칙 날짜 파서**(수집기 정의 파일과 같은 파서를 TS로 옮기거나 같은 규칙으로 구현)로 바꾼다. 연도가 원문에 없으면 빈칸. 파서가 못 바꾸면 빈칸.
- **FR-012** 확신이 `low`인 칸은 값을 채우되 확인 화면에서 표시하고, 단체가 그 칸을 건드리지 않고 보내려 하면 «표시된 칸을 한 번 봐 주세요»로 한 번 묻는다. `none`은 빈칸. 날짜 칸은 `low`여도 원문 파싱이 되는 경우에만 채운다.
- **FR-013** AI 지시문에 «인쇄되지 않은 것은 null», «소개 글을 쓰지 말 것», «QR을 해석하지 말 것»을 넣고, 결과를 서버에서 다시 검사한다(칸 밖 키 버림, 글자 수 상한, 날짜 형식).
- **FR-014** AI 실행 위치: **서버 경로(Next.js API, Vercel `icn1`)**를 기본안으로 둔다(US2가 즉시 확인 화면을 요구하므로). 다른 안과 비교는 research.md «R3». 서버 경로는 로그인 검사·하루 한도·월 상한 검사 뒤에만 AI를 부른다.
- **FR-015** 비용 집계: 요청마다 입력·출력 토큰 수와 추정 금액을 표(가칭 `ai_usage`)에 남기고, 이달 합계가 상한(«정할 것» 1)에 닿으면 AI를 부르지 않고 빈 양식으로 이어간다. 운영 대시보드에 이달 건수·금액을 보인다.
- **FR-016** AI 키는 서버 전용 환경 변수(예: `GEMINI_API_KEY`)로만 둔다. `NEXT_PUBLIC_` 이름으로 두지 않는다(브라우저 묶음에 실린다).
- **FR-017** 공급자의 무료 등급이 입력을 제품 개선에 쓰는 경우(research.md R2 — Gemini 무료 등급은 «쓴다») 이 기능에는 **유료 등급 키**만 쓴다. 리플렛에 개인 연락처가 있을 수 있기 때문이다.

**확인·제출·저장**
- **FR-020** 제출 기록 표(가칭 `leaflet_submissions`): id, user_id, image_path, image_hash, status(`uploaded` → `read` → `confirmed` → `published`/`rejected`), ai_result jsonb(원문·확신 포함), confirmed jsonb(단체 확정 값), rights_ok·accuracy_ok(체크 여부), rights_text_version(체크 문구 판), contact_public(참/거짓), raw_post_id, 시각들. RLS: 회원은 자기 것만 넣고 읽고, `confirmed` 전까지 자기 것의 confirmed 칸만 고친다. 관리자는 모두. 익명은 없음.
- **FR-021** 단체가 보내면(서버 경로, 서비스 키) `raw_posts`에 한 줄을 **처음부터 `status='REVIEW'`로** 넣는다. `source='단체 제공'`, `source_id=제출 id`, `source_url`은 (a)/(b) 결정에 따름, `content`는 기존 형식(`title`, `description`, `ai_suggestion{date_start, date_end, time, venue, region, price, extracted_by:'leaflet', confirmed_by:'group'}`, `review_bucket:'leaflet'`). 기존 `save_raw_post`는 상태를 `COLLECTED`로 덮어쓰므로(인스타 수집기 주석) 쓰지 않는다. `REVIEW`는 `publish_verified.py`의 대상(`COLLECTED`·`PENDING`)이 아니라 정기 자동 공개에 걸리지 않는다.
- **FR-022** `content.description`에는 단체가 «더 알려 줄 것»에 직접 쓴 글만 넣는다. AI가 쓴 소개 글은 없다.
- **FR-023** 007 제보(`reports.kind='tip'`)와는 별도 표로 두되, 확인 화면은 007 `TipForm`의 칸·검사(`checkTip`)를 다시 쓴다. 007 표에 `kind='leaflet'`를 더하는 안은 research.md R4에 비교.

**검토·공개**
- **FR-030** 관리자 «단체 제공» 검토 화면: 이미지(비공개 버킷의 서명 주소, 짧은 유효 시간), AI 값 / 단체 값 / 다른 칸 표시, 체크 기록, 제출 회원, 원본 링크 열림 여부. 동작: 공개 / 고쳐서 공개 / 단체에 묻기 / 반영 안 함.
- **FR-031** 공개는 `publish_verified.py`와 같은 날짜·중복 규칙을 거친다(같은 코드를 `--ids`로 부르거나 같은 규칙으로). 원본 링크 규칙은 아래 (a)/(b) 결정에 따른다.
- **FR-032** 공개 포스터(`poster_image_url`)는 «원본 파일» 표시가 있고 권리 체크가 있는 이미지일 때만, 공개 버킷으로 **복사**해 쓴다(비공개 원본은 그대로). 자르기는 비율 맞춤만(BRAND_GUIDE 5-5). 출처 표기 `포스터·정보: <단체 이름>(단체 제공)`.

### 원본 링크 문제 — «원본 링크가 지금 열린다(HTTP<400)»와의 충돌

헌장 I과 `publish_verified.py`(검증 기준 2, `collector/utils.py check_link`)는 공개 행사마다 **지금 열리는 원본 링크**를 요구한다. 리플렛 사진에는 원본 링크가 없다. 두 안:

**(a) 단체의 공식 SNS 게시물·페이지 주소를 원본으로 요구한다**
- 확인 화면에 «공식 안내 주소(필수)»를 둔다(007 제보와 같은 규칙). 공개 때 `check_link`를 그대로 거친다.
- 좋은 점: 헌장·발행 코드를 바꾸지 않는다. 피카 밖에 공개 근거가 있어 «확인한 정보»의 뜻이 그대로다. 행사 상세의 «원본 보기»가 단체 쪽으로 간다.
- 나쁜 점: 누리집·SNS 게시물이 없는(카톡·현수막·종이 리플렛만 있는) 단체는 등록할 수 없다 — 이 기능과 012가 겨냥한 «사각지대» 단체가 바로 이들이다. 게시물이 리플렛보다 늦게 올라오면 기다려야 한다. 인스타그램 게시물 주소가 `check_link`(aiohttp 요청)에 400 미만으로 응답하는지는 이 세션에서 확인하지 않았다 — 계획 단계에서 실제 주소로 확인할 것.

**(b) 새 출처 종류 «단체 제공»: 원본은 피카가 보관하는 리플렛 이미지 페이지**
- 공개할 때 `/leaflets/<제출 id>` 같은 피카 페이지를 만들고(리플렛 이미지 + «○○가 2026-11-26에 피카에 직접 제공» 표시), 그것을 `original_url`로 쓴다. 단체 SNS 주소가 있으면 함께 적는다.
- 좋은 점: 온라인 흔적이 없는 단체도 등록할 수 있다. 원본(리플렛 이미지)이 피카 안에 남아 날짜를 다시 대조할 수 있다.
- 나쁜 점: 링크 검사가 자기 자신을 확인하는 셈이라 «지금 열린다»가 검증 구실을 못 한다. 대신할 검증이 필요하다 — 예: 단체 확인(약관 제3조: 고유번호증·공식 계정, 또는 동의서 서명)을 마친 회원만 «단체 제공»으로 공개, 그 외 회원은 (a)만. 헌장 I의 문구를 고쳐야 한다(Governance: 개정은 사용자 승인, 뜻이 바뀌면 MAJOR). 리플렛 이미지가 **공개**되므로 권리·개인정보 부담이 커지고(아래), 단체가 삭제를 요청하면 7일 안에 페이지와 이미지를 내려야 한다(동의서 2·4). 발행 코드에 출처별 예외가 생긴다.

섞는 안: 주소가 있으면 (a), 없으면 확인된 제휴 단체에 한해 (b). 고르는 것은 운영자(«정할 것» 2).

### 개인정보

- 리플렛에는 담당자 개인 휴대전화(`010-`), 개인 이메일, 출연자 얼굴·이름, 계좌번호(후원 안내)가 들어 있을 수 있다. 약관 제5조 3항은 단체가 개인 연락처를 «제공하지 않는다»고 하고, 제공되면 «게재하지 않고 지운다»고 한다.
- **FR-040** AI 결과의 `contact`에 `010`·`011`·`016`·`017`·`018`·`019`로 시작하는 번호나 개인 메일이 있으면 «공개하지 않음»이 기본이다. 단체가 «공개해도 되는 대표 연락처»(동의서 칸과 같은 말)라고 고를 때만 공개 후보.
- **FR-041** 계좌번호 형식은 칸에 옮기지 않는다.
- **FR-042** (b)를 고르거나 포스터로 공개할 이미지에 개인 휴대전화가 **보이면** 그 이미지는 공개하지 않고, 단체에 번호가 없는 판을 요청한다(가리기는 BRAND_GUIDE 5-5 «포스터는 손대지 않는다»와 부딪치므로 하지 않는다 — 다르게 하려면 운영자에게 묻는다).
- **FR-043** 비공개 버킷의 원본 이미지 보유 기간: 공개된 것은 행사 종료 후 N일, 반영 안 한 것은 처리 후 N일(«정할 것» 7). 개인정보처리방침(`/privacy`)에 «리플렛 이미지, 읽은 내용, 보낸 회원 계정, 보유 기간, AI 처리 위탁(공급자 이름)»을 더한다.
- **FR-044** AI 공급자에 이미지를 보내는 것은 개인정보 처리 위탁에 해당할 수 있다 — 처리방침에 공급자를 적고, 업로드 화면에 «글자를 읽기 위해 ○○ AI에 이미지를 보냅니다» 한 줄을 둔다. 법률 검토 항목에 더한다.

### 권리 확인 체크 (약관 제5조·동의서 3)

- **FR-050** 올리기 전에 체크 한 개(필수), 보내기 전에 체크 한 개(필수):
  - 올리기 전(초안): «이 이미지의 포스터·사진에 다른 권리자(디자이너·사진가 등)가 있으면, 피카 게재를 허락받았습니다. 관객·출연자의 개인 연락처는 넣지 않았습니다.»
  - 보내기 전(초안): «위 내용이 리플렛과 같고 사실과 다르지 않습니다. 바뀌면 알리겠습니다.»
  - 선택: «이 이미지를 포스터로 써도 됩니다(원본 파일입니다)» — 안 고르면 글 정보만 게재(동의서 1-3의 «동의하지 않음»과 같음).
- **FR-051** 체크 문구는 판 번호를 붙여 저장한다(`rights_text_version`). 문구를 바꾸면 판을 올린다. 최종 문구는 운영자가 정한다(«정할 것» 4).

### Key Entities

- **leaflet_submissions** — 단체 제출 한 건(이미지 경로, AI 결과, 단체 확정 값, 체크 기록, 상태, 연결된 raw_post).
- **leaflets 버킷** — 비공개 원본 이미지.
- **raw_posts (기존)** — `source='단체 제공'`, `status='REVIEW'`, `content.review_bucket='leaflet'`.
- **ai_usage** — 요청별 토큰·추정 금액·결과(성공·실패), 월 합계 계산용. 관리자만 읽는다.
- **events (기존)** — 공개 결과. `source`, `original_url`은 (a)/(b)에 따름.

## Success Criteria / 끝 조건 (헌장 V)

무엇을 확인하면 끝인지. 각 항목은 실제로 실행한 명령·숫자·화면으로 보고한다.

**정확도 시험 (구현 전 먼저 — 모델 고르기에도 씀)**
- **SC-001** 시험 묶음 20장(운영자가 고른 실제 리플렛·포스터: 인쇄 파일 10, 휴대폰 사진 10, 연도 없는 것 3장 이상, 행사 여러 개 1장 이상)을 만들고, 사람이 칸별 정답표를 먼저 적는다.
- **SC-002** **날짜 칸 오답 0건**(빈칸은 허용, 틀린 값은 0). 연도 없는 리플렛은 날짜 칸이 모두 빈칸.
- **SC-003** 제목·장소 칸 정답률(빈칸 제외 값이 정답과 같은 비율)을 숫자로 보고. 목표 제목 90%·장소 80% 이상 — 못 미치면 모델·지시문을 바꾸거나 운영자에게 보고하고 멈춤.
- **SC-004** 인쇄되지 않은 칸에 값을 채운 경우(지어냄) 0건.
- **SC-005** 한 장당 실제 토큰 수와 금액을 20장 평균·최대로 보고(research.md R2 추정과 비교).

**보안·흐름**
- **SC-010** 익명: 버킷 파일 읽기·목록 실패, `leaflet_submissions`·`ai_usage` 읽기 `[]`·쓰기 401(REST로 확인).
- **SC-011** 회원 A가 회원 B의 이미지 경로를 직접 요청하면 실패.
- **SC-012** 11MB 파일·PDF가 버킷 설정에서 거절됨.
- **SC-013** 저장된 이미지에 EXIF GPS가 없음(올린 사진의 메타데이터를 읽어 확인).
- **SC-014** 단체가 보낸 직후 `raw_posts`에 `REVIEW` 1줄, `events`에는 0줄. `publish_verified.py --dry-run`을 돌려도 그 줄이 대상에 없음.
- **SC-015** 운영자 «공개» 뒤 `events` 1줄, 원본 링크·출처 표기·포스터 칸이 결정한 방식대로. 공개 상세 화면을 브라우저로 확인.
- **SC-016** 월 상한을 시험값(예: 0원)으로 두면 AI를 부르지 않고 빈 양식이 나옴, `ai_usage`에 새 줄 없음.
- **SC-017** 키 이름 검사: 프론트 빌드 결과에 AI 키 이름·값이 없음(`NEXT_PUBLIC_`로 시작하는 AI 키 0개).
- **SC-018** `npx tsc --noEmit` 통과, 배포 뒤 배포 주소에서 SC-010·SC-014 다시 확인.

## Assumptions

- 단체 담당자는 007과 같은 구글·카카오 로그인 회원이다(비로그인 허용 여부는 «정할 것» 3).
- 회원이 실제로 그 단체 사람인지는 이 기능이 증명하지 않는다. 운영자 검토(US3)와 (b)의 «확인된 제휴 단체» 조건이 그 몫이다.
- 한 달 올리기 양은 처음 수십~수백 장으로 본다(근거 없음 — 운영 시작 후 `ai_usage`로 확인).
- 기존 `collector/ai_extractor.py`(Gemini, 비용 문제로 꺼 둠)는 켜지 않는다. 이 기능은 별도 경로·별도 상한으로 돈다.

## 정할 것 (운영자)

1. **AI 공급자·모델과 월 비용 상한** — 후보와 단가는 research.md R2. 지금 키가 있는 것은 Gemini(`GEMINI_API_KEY`, 수집기 `.env.local`)뿐이고, 그 키가 무료·유료 등급인지와 Vercel 환경 변수에 있는지는 확인하지 않았다. 추정 한 장당 약 3~30원(모델·출력 길이에 따라). 상한 예: 월 1만 원. 유료 등급 키를 쓸지(FR-017)도 함께.
2. **원본 링크: (a) 단체 공식 SNS·페이지 주소 필수 / (b) 새 출처 «단체 제공»(피카가 보관하는 리플렛 페이지가 원본) / 섞는 안** — (b)나 섞는 안이면 헌장 I 개정이 필요하다.
3. **로그인하지 않은 단체도 올릴 수 있게 할지** — 허용하면 연락처(메일) 칸·스팸 방지(하루 한도를 IP로)·개인정보 수집 동의가 더 필요하다. 007은 «로그인 회원만»으로 정했다.
4. **권리 확인 체크 문구** — FR-050 초안 그대로 / 고침. 법률 검토 때 약관 제5조와 같이 볼지.
5. **AI 실행 위치** — 기본안 서버 경로(즉시 확인 화면) / 수집기(PC, 하루 두 번, 단체는 나중에 확인) — research.md R3.
6. **헌장 IV에 예외를 문구로 적을지** — 적으면 MINOR 개정(`/speckit-constitution`).
7. **원본 이미지 보유 기간** — 예: 공개분 행사 종료 후 30일, 반영 안 한 것 처리 후 30일.
8. **휴대폰 사진만 있을 때 포스터 칸** — 비움(헌장 I 그대로, 기본안) / 운영자 판단으로 사진을 포스터로 허용.
